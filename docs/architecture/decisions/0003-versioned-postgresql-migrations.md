# 0003 — Версионируемые миграции PostgreSQL через Alembic

## Status

Accepted

## Context

Application metadata должна храниться в отдельной схеме PostgreSQL и
эволюционировать воспроизводимо. Создание объектов при старте API не даёт
истории версий и затрудняет безопасное повторное применение изменений.

## Decision

Для application schema `graph_blizz` используется Alembic с линейной историей
ревизий. Подключение строится из существующих типизированных PostgreSQL settings,
а секреты передаются только через окружение. Таблица версии Alembic остаётся в
стандартной схеме `public`, чтобы первая миграция сама создавала application
schema и полностью описывала её жизненный цикл.

## Consequences

`alembic upgrade head` одинаково применим к чистой и уже актуальной базе;
следующие application tables должны явно создаваться в схеме `graph_blizz`.
Оператору нужно запускать миграции до старта версии приложения, которая ожидает
новую схему. У роли PostgreSQL должны быть права на создание схемы и объектов.

## Alternatives considered

- Создавать схему через bootstrap SQL Docker: история схемы оказалась бы вне
  application migrations.
- Создавать таблицы при старте API: параллельные старты и откаты были бы
  неуправляемыми.
- Хранить таблицу версии внутри `graph_blizz`: Alembic требует существования
  этой схемы до выполнения первой versioned migration.
